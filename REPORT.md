# Disk Paxos Project Report

## 1. Project Overview

This project studies and implements Disk Paxos, a consensus algorithm introduced by Gafni and Lamport. The goal of the algorithm is to allow a set of processors to agree on a single value using persistent disks instead of direct message passing between processors.

The Go implementation in this repository models:

- processors as concurrent Go proposers;
- disks as independent Redis instances;
- disk blocks as persisted JSON values containing ballot and accepted-value information;
- quorum reads and writes over a majority of disks.

The project currently focuses on the Go implementation. A second implementation in another course language remains to be added.

## 2. Formal Model

The formal reference model was taken from the official `tlaplus/Examples` repository and added under `tla/`.

The relevant files are:

- `tla/Synod.tla`
- `tla/DiskSynod.tla`
- `tla/HDiskSynod.tla`
- `tla/MC_HDiskSynod.tla`
- `tla/MC_HDiskSynod.cfg`

The purpose of the TLA+ model is to describe the concurrent algorithm mathematically, independently of the Go implementation. Instead of describing one concrete execution, the model defines:

- valid initial states;
- valid transitions between states;
- processor phases;
- disk state;
- failure and recovery behavior;
- invariants that must hold in every reachable state.

TLC, the TLA+ model checker, explores reachable states generated by the transition relation and checks the invariants in each state.

## 3. TLC Configuration

The model checking configuration is defined in `tla/MC_HDiskSynod.cfg`.

The verifier inputs are:

- `N = 3`: three processors;
- `Inputs = {in1, in2}`: two possible input values;
- `BallotCountPerProcess = 2`: each processor has two ballot values in the finite model;
- `Disk = {1, 2}`: two modeled disks;
- `Ballot <- BallotImpl`: replaces the abstract ballot function with a finite implementation;
- `IsMajority <- IsMajorityImpl`: replaces the abstract majority predicate with a finite implementation;
- `INIT HInit`: starts from the initialized high-level model state;
- `NEXT HNext`: uses the high-level transition relation;
- `INVARIANTS HInv1 HInv2 HInv3 HInv4 HInv6`: checks the listed invariants.

The most important invariant for this project is `HInv6`, which captures the consensus safety property:

> every processor output is either empty or equal to the single chosen value.

In the Go implementation, this corresponds to the requirement that all successful proposers decide the same value.

## 4. TLC Execution

TLC was installed locally by downloading the official `tla2tools.jar` into `tools/`.

The Makefile includes:

```bash
make tla-tools
make tla-check
make tla-check-output
```

The TLC command uses parallel workers:

```bash
java -XX:+UseParallelGC -cp ../tools/tla2tools.jar tlc2.TLC -workers auto -config MC_HDiskSynod.cfg MC_HDiskSynod.tla
```

The original configuration was run with 16 workers. The run was stopped manually after approximately five hours because the generated state/checkpoint data reached around 60-68 GB and the queue was still growing.

Last recorded progress:

```text
15,197,757,628 states generated
996,823,546 distinct states found
165,552,569 states left on queue
```

No invariant violation, deadlock, or TLC error was reported in the explored part of the state space. However, because the run was stopped before the queue became empty, this run cannot be presented as a completed proof for the full configured model.

The result is still useful because it demonstrates state-space explosion: even a small finite model with three processors, two input values, two ballots per processor, and two disks generates an extremely large number of interleavings.

## 5. Go Implementation

The Go implementation is organized as follows:

- `cmd/concurrent_proposers`: runs multiple concurrent processors trying to decide a value;
- `cmd/clear_disks`: clears Redis disk state;
- `internal/block`: defines the disk block structure;
- `internal/disk`: wraps Redis operations used as disk reads/writes;
- `internal/processor`: implements the Disk Paxos processor logic;
- `internal/config`: loads and validates runtime configuration;
- `internal/logger`: creates the development logger.

Redis instances are used as independent virtual disks. Each processor writes its block using keys such as `block-1`, `block-2`, etc.

The Go block structure is:

```go
type Block struct {
    Mbal int
    Bal  int
    Inp  string
}
```

This maps to the TLA+ `DiskBlock` fields:

- `mbal` -> `Mbal`;
- `bal` -> `Bal`;
- `inp` -> `Inp`.

## 6. Mapping Between TLA+ and Go

The main correspondence between the formal model and the implementation is:

- `Proc` maps to Go processors/proposers;
- `Disk` maps to Redis instances;
- `DiskBlock` maps to `internal/block.Block`;
- `input[p]` maps to the value passed to `Processor.Propose`;
- `output[p]` maps to the value returned by `Processor.Propose`;
- majority disk sets map to `DiskCount/2 + 1`;
- TLA+ processor phases map to explicit Go processor phases.

The Go processor now uses explicit phases:

- `PhaseRecovery`;
- `PhaseScout`;
- `PhaseCommit`;
- `PhaseDone`.

This was added after comparing the initial Go implementation with the TLA+ model.

## 7. Inconsistencies Found and Fixed

The initial Go implementation was compared against the TLA+ files. Several differences were found.

### Missing Phase 0 Recovery

The TLA+ model includes a phase 0 recovery step where a processor reads its own previous blocks from a quorum of disks before starting a new ballot.

The original Go implementation started processors with an empty local block.

Fix:

- added `PhaseRecovery`;
- added recovery logic that reads the processor's own persisted blocks;
- restored the highest accepted value before starting a new ballot.

### Proposed Value Written Too Early

In the TLA+ model, phase 1 updates the maximum ballot. The proposed or adopted value is written only after phase 1 succeeds.

The original Go code wrote the proposed value during phase 1. This made the Go state less consistent with the TLA+ invariant that an empty accepted ballot corresponds to no accepted input.

Fix:

- phase 1 no longer writes the fresh proposed value;
- the value is selected/adopted after phase 1 reads;
- phase 2 writes the accepted value.

### Reading Own Block During Active Phases

The TLA+ model reads other processors' blocks during phase 1 and phase 2.

The original Go implementation read all blocks, including its own.

Fix:

- added separate read helpers for all blocks, own blocks, and other processors' blocks;
- phase 1 and phase 2 use the other-processors read helper.

## 8. AI Tool Usage

The initial repository and implementation were created manually, while ChatGPT/Codex was used as an assistant for questions and implementation guidance.

AI assistance was used for:

- understanding the TLA+ Disk Paxos specification;
- mapping TLA+ concepts to Go structures;
- identifying inconsistencies between the formal model and the Go implementation;
- refactoring the Go implementation to better match the TLA+ phases;
- designing the test strategy;
- adding GoMock-based unit tests;
- adding Redis integration tests with testcontainers;
- adding Makefile commands for tests and TLC.

The AI-generated suggestions were manually reviewed and adjusted. One example was the placement of the `Store` interface: it was first introduced in the disk package, then moved to the consumer package, `internal/processor`, following the Go convention that consumers define interfaces.

A separate interaction log is kept in `AI_INTERACTION.md`.

## 9. Testing Strategy

The Go implementation is tested using:

- unit and table-driven tests;
- generated GoMock mocks for processor tests;
- Redis integration tests through testcontainers;
- the Go race detector.

Makefile commands:

```bash
make test
make test-table
make test-race
make test-integration
make test-all
```

All Go test commands use `-count=1` so results are not served from the Go test cache.

Integration tests are behind the `integration` build tag and require Docker access.

## 10. Unit Tests

Unit tests were added for:

- block JSON serialization and deserialization;
- config validation;
- disk client edge cases;
- logger construction;
- processor ballot generation;
- phase 0 recovery;
- quorum failure on writes;
- quorum failure on reads;
- adoption of the highest accepted value during phase 1.

Processor tests use a generated GoMock mock for the consumer-owned `processor.Store` interface. The generated mock is placed under:

```text

```

## 11. Integration Tests

A Redis integration test was added for the disk client using testcontainers.

The test starts a real `redis:7-alpine` container and verifies:

- `SetBlock`;
- `ReadBlocks`;
- `ReadAllBlocks`;
- `DeleteAllBlocks`.

The test is located in:

```text
internal/disk/client_integration_test.go
```

It is enabled with:

```bash
go test -count=1 -tags=integration ./...
```

or:

```bash
make test-integration
```

## 12. Race Detector

The Go race detector is used with:

```bash
make test-race
```

This runs:

```bash
go test -count=1 -race ./...
```

The race detector is relevant because the implementation performs parallel reads and writes over disk clients using goroutines.

## 13. Tool-Detected Problems and Corrections

During the project, tool-assisted review and tests helped identify and correct issues.

The main correctness issue found during comparison with the TLA+ model was that the Go implementation wrote the input value too early, during phase 1. The TLA+ model showed that phase 1 should only establish the ballot and read/adopt existing accepted values. The Go implementation was corrected so the accepted value is written in phase 2.

The tests then captured this behavior by asserting that phase 1 does not write a non-empty input and that phase 2 writes the adopted value.

The TLA+ run also demonstrated the practical cost of exhaustive state-space exploration. The run did not find a violation in the explored states, but it showed that the original configuration is too large to complete comfortably on the available machine.
